\section{Architecture Design}

\subsection{High-Level Architecture}

The system adopts a \textbf{modular monolith} with clean layered boundaries to balance Lab 4 rapid delivery while maintaining extensibility for future modules (elections, meetings, etc.).

\textbf{Tech Stack:}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Frontend:} Next.js 14 + React + TypeScript + Tailwind CSS + shadcn/ui + TanStack Query (React Query)
  \item \textbf{Backend:} NestJS + TypeScript + Passport.js (JWT) + Prisma ORM
  \item \textbf{Database:} PostgreSQL 14+ (docker-compose for dev)
  \item \textbf{Notifications:} Email (SMTP); in-app logging
  \item \textbf{DevOps:} GitHub Actions CI/CD, Docker, Docker Compose
\end{itemize}

\subsection{Backend: Clean Layered Architecture}

NestJS backend uses \textbf{four-tier layering} to enforce constitutional constraint encoding:

\begin{enumerate}
  \item \textbf{Presentation Layer (Controllers)} --- HTTP endpoints, input validation, response mapping
  \item \textbf{Application Layer (Services)} --- Use-case orchestration, workflow state machines
  \item \textbf{Domain Layer (Policies + Entities)} --- Business rule enforcement, constitutional validation
  \item \textbf{Infrastructure Layer (Repositories, DB, Email)} --- Data access, external service integration
\end{enumerate}

\textbf{Policy-Driven Design (Strategy Pattern):} Constitutional rules encoded separately:
\begin{itemize}[noitemsep]
  \item \texttt{MembershipPolicy} --- Validates registration eligibility per Articles VI--VII
  \item \texttt{EligibilityPolicy} --- Enforces candidacy constraints (year, EC experience) per Articles XIV--XV
  \item \texttt{AuthorityPolicy} --- Enforces Chief Patron override, EC abolition power
  \item \texttt{FinancialPolicy} --- Validates transaction categories, co-signature rules, immutability
  \item \texttt{AttendancePolicy} --- Auto-flags 3rd consecutive absence per Article XVI
\end{itemize}

\subsection{Request Lifecycle Example}

\textbf{Scenario:} Member registration (FR-CSC-001, US-CSC-001)

\begin{enumerate}[leftmargin=1.5em]
  \item User submits registration form: [email, password, firstName, lastName, studentID, batch]
  \item \texttt{POST /auth/register} routed to \texttt{AuthController}
  \item Controller validates schema (Joi/Zod input validation)
  \item Service calls \texttt{MembershipPolicy.canRegister(studentID, batch)}
  \item Policy checks: active CSEDU student, not duplicate member, batch valid
  \item If valid: create User + Member records via Prisma; hash password (Argon2)
  \item Send confirmation email (async, logged to audit trail)
  \item Return 201 with JWT token + member profile
  \item Frontend updates state; user redirected to dashboard
\end{enumerate}

\subsection{Extensible EC Committee Design (No Schema Change for New Posts)}

To avoid redesign when a new EC post is introduced, treat EC posts as configuration data:

\begin{itemize}[leftmargin=1.5em]
  \item Keep \textbf{system roles} (General Member, Moderator, Chief Patron) in \texttt{roles}
  \item Keep \textbf{EC post catalog} in \texttt{ec\_posts} (President, VP, Treasurer, or any future post)
  \item Assign members to posts per term through \texttt{ec\_appointments}
  \item Validate candidacy from \texttt{ec\_posts.minYear} and \texttt{ec\_posts.minEcYears}
  \item Use \texttt{permissions} by role; use post-specific policies from \texttt{ec\_posts}
\end{itemize}

Adding a new post next year is only:
\begin{enumerate}
  \item Insert one row in \texttt{ec\_posts} with title and eligibility rules
  \item Map permissions/policies (if needed)
  \item No migration to add new columns, no controller rewrite
\end{enumerate}

\subsection{Schema Constraints and Rationale}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Uniqueness:} \texttt{UNIQUE(email)}, \texttt{UNIQUE(studentID)} prevent duplicates
  \item \textbf{Term Safety:} \texttt{ec\_terms} cannot overlap; one active term at a time
  \item \textbf{Post Safety:} \texttt{UNIQUE(termId, postId)} ensures one active holder per post per term
  \item \textbf{Status Enums:} Member states (Active $\to$ Cancelled/Expired) prevent invalid transitions (immutable per FR-CSC-002)
  \item \textbf{Append-Only Ledger:} Transactions table has no UPDATE/DELETE permissions; new entries only (per FR-CSC-020, NFR-CSC-011)
  \item \textbf{Financial Constraints:} \texttt{CHECK (amount > 0)} enforced at schema + service layer
  \item \textbf{Audit Trail:} \texttt{createdBy}, \texttt{createdAt}, \texttt{updatedAt} timestamp all tables
  \item \textbf{Foreign Key Integrity:} All user/role references validated; orphaned data prevented
\end{itemize}

\subsection{Entity Relationships (SRS Section 7.2 Mapping)}

Key relationships per SRS:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{users 1:1 members} --- User has one member profile (FR-CSC-001)
  \item \textbf{users N:N roles} via \texttt{user\_roles} --- Supports multiple concurrent permissions (FR-CSC-024)
  \item \textbf{ec\_terms 1:N ec\_appointments} --- Each term has multiple post assignments (FR-CSC-004)
  \item \textbf{ec\_posts 1:N ec\_appointments} --- Same post reused across terms without schema change (FR-CSC-004)
  \item \textbf{members 1:N events} --- Member organizes multiple events (FR-CSC-015)
  \item \textbf{members 1:N volunteers} --- Member registers as volunteer for events (FR-CSC-017)
  \item \textbf{members 1:N transactions} --- Treasurer creates append-only entries (FR-CSC-020)
  \item \textbf{roles 1:N permissions} --- Role grants endpoint permissions (FR-CSC-024)
\end{itemize}

\subsection{Migration Strategy}

\begin{enumerate}
  \item \texttt{prisma/schema.prisma} generated from above design
  \item \texttt{prisma migrate dev --name init} creates migrations/
  \item \texttt{prisma db seed} loads test data (5 members, 2 roles, 3 events, 10 transactions)
  \item No archival tables in v1; defer to Lab 5+ per SRS 7.3
\end{enumerate}

\section{Critical Flows (Lab 4)}

\subsection{Flow 1: Member Registration to Dashboard (FR-CSC-001, US-CSC-001)}

\textbf{Actors:} General member, system

\textbf{Preconditions:}
\begin{itemize}[noitemsep]
  \item User is a current CSEDU student (verified against batch/studentID format)
  \item No existing member account for this studentID
\end{itemize}

\textbf{Flow Steps:}
\begin{enumerate}[leftmargin=1.5em]
  \item User navigates to \texttt{/auth/register}
  \item Frontend displays form: [email, password (confirmation), firstName, lastName, studentID, batch]
  \item User fills form, ticks agreement checkbox, submits
  \item Post \texttt{/auth/register} with credentials
  \item Backend validates schema (Joi/Zod) — returns 400 if missing/invalid
  \item Backend calls \texttt{MembershipPolicy.canRegister(studentID, batch)}
  \item Policy checks: batch $\in$ [2021, 2022, ...], studentID format valid, no duplicate
  \item If valid: create User (hash password Argon2), create Member (status=Active)
  \item Log action to audit\_logs (actor=system, action=MEMBER\_REGISTERED)
  \item Send confirmation email (async, timeout 5sec)
  \item Return 201 \{token: JWT, user: \{id, email, roles: ["General Member"]\}\}
  \item Frontend stores JWT in httpOnly cookie, redirects to \texttt{/dashboard}
  \item Dashboard loads member profile (GET \texttt{/members/me}), displays greeting + upcoming events
\end{enumerate}

\textbf{Success Criteria:}
\begin{itemize}[noitemsep]
  \item Member appears in Active members list
  \item Confirmation email received within 2 minutes
  \item User can log in with credentials
  \item Dashboard shows correct member status and batch
\end{itemize}

\textbf{Failure Cases:}
\begin{itemize}[noitemsep]
  \item Duplicate studentID: 409 Conflict, message: "Student ID already registered"
  \item Invalid batch: 400 Bad Request, message: "Batch must be valid CSEDU year"
  \item Email already exists: 409 Conflict, message: "Email already in use"
  \item Network failure on confirmation email: logged; user still registered; retry notify later
\end{itemize}

\subsection{Flow 2: Financial Transaction Entry to Ledger View (FR-CSC-020, US-CSC-006)}

\textbf{Actors:} Treasurer, Moderator, system

\textbf{Preconditions:}
\begin{itemize}[noitemsep]
  \item User has Treasurer permission via \texttt{user\_roles} (or active Treasurer post in \texttt{ec\_appointments})
  \item Valid transaction category exists: [Donation, RegFee, Expenditure, Dept]
  \item Supporting document reference provided (e.g., receipt ID, check no.)
\end{itemize}

\textbf{Flow Steps:}
\begin{enumerate}[leftmargin=1.5em]
  \item Treasurer logs in, navigates to \texttt{/ec/finance}
  \item Frontend displays ledger table + "Add Transaction" button
  \item Treasurer clicks "Add Transaction", opens modal: [type (Income/Exp), amount, category, reference]
  \item Treasurer enters: type=Income, amount=5000, category=Donation, reference=DonorName-001
  \item Post \texttt{/finance/transactions} with transaction object
  \item Backend validates schema: amount > 0, type $\in$ \{Income, Exp\}, category valid
  \item Backend calls \texttt{FinancialPolicy.validateTransaction(tx, treasurerID)}
  \item Policy confirms: amount valid, category valid, required fields present
  \item Backend creates Transaction record with createdBy=treasurerID, immutable flag set
  \item Log action to audit\_logs: \{actor: treasurerID, action: TRANSACTION\_CREATED, resource: transaction.id\}
  \item Return 201 \{transaction: \{id, type, amount, date, category, balance\}\}
  \item Frontend updates ledger table with new entry; shows running balance
  \item Moderator (separate session) loads ledger via GET \texttt{/finance/ledger}
  \item Backend queries all transactions, calculates balance (sum income — sum expenditure)
  \item Moderator sees same entry with balance reflected
  \item (Future Lab 5) No DELETE operation available on transactions
\end{enumerate}

\textbf{Success Criteria:}
\begin{itemize}[noitemsep]
  \item Transaction appears in ledger with correct amount and category
  \item Running balance updates correctly (previous balance ± new amount)
  \item Audit log shows transaction creation with timestamp and actor
  \item Moderator can view and verify ledger
  \item Transaction is immutable (no edit/delete UI or API route)
\end{itemize}

\textbf{Failure Cases:}
\begin{itemize}[noitemsep]
  \item Negative amount: 400 Bad Request, message: "Amount must be greater than 0"
  \item Invalid category: 400 Bad Request, message: "Category must be one of: [Donation, RegFee, ...]"
  \item Non-Treasurer tries to create: 403 Forbidden, message: "Only Treasurer role can create transactions"
  \item Missing reference: 400 Bad Request, message: "Reference document ID required"
\end{itemize}

\section{Security and Access Control}

\subsection{Authentication (FR-CSC-024)}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Password Hashing:} Argon2id via bcryptjs library (per NFR-CSC-003)
  \item \textbf{JWT Tokens:} 15-minute expiry on access token; 7-day refresh token in httpOnly cookie
  \item \textbf{Token Claims:} Payload includes user.id, user.roles[], user.email, activeTermId
  \item \textbf{Refresh Flow:} POST \texttt{/auth/refresh} exchanges refresh token for new access token (no user interaction)
  \item \textbf{Logout:} Clear refresh cookie; client removes JWT from memory
\end{itemize}

\subsection{Authorization: RBAC Enforcement (FR-CSC-024, NFR-CSC-005)}

Every endpoint enforces role checks:

\begin{tabular}{|l|l|l|}
\hline
\textbf{Endpoint} & \textbf{Required Role} & \textbf{Enforced At} \\
\hline
POST /auth/register & (none) & Schema validation only \\
\hline
GET /members/me & General Member+ & Auth middleware (JWT required) \\
\hline
GET /events & General Member+ & Auth middleware \\
\hline
POST /events & EC Member (organizer) & Controller guard, returns 403 if General Member \\
\hline
POST /finance/transactions & Treasurer & Controller guard, \texttt{FinancialPolicy.hasPermission()} \\
\hline
POST /finance/transactions & Moderator (view only) & GET \texttt{/finance/ledger} permitted; POST forbidden \\
\hline
\end{tabular}

\textbf{Defense-in-Depth:}
\begin{itemize}[noitemsep]
  \item Frontend route guards prevent navigation to protected pages
  \item Backend middleware verifies JWT before reaching controller
  \item Backend controller re-checks role (never trust frontend)
  \item 403 error logged to audit trail with denied user ID
\end{itemize}

\subsection{Data Protection}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{HTTPS/TLS 1.2+:} Enforced in production; dev uses localhost (per NFR-CSC-004)
  \item \textbf{Immutable Ledger:} Transaction DELETE never exists; UPDATE blocked via ORM + DB policy
  \item \textbf{Input Validation:} All POST/PUT endpoints use Joi/Zod schema validation (prevents SQL injection, XSS)
  \item \textbf{Audit Logging:} Critical actions (login, register, transaction, role change) logged with timestamp, actor, resource ID
  \item \textbf{Query Parameterization:} Prisma ORM uses parameterized queries automatically
\end{itemize}

\subsection{Future Security Considerations (Labs 5+)}

\begin{itemize}[noitemsep]
  \item Two-factor authentication for Moderator/Chief Patron roles
  \item Digital signature workflows for multi-party approvals (certificates, constitution changes)
  \item Rate limiting on login/API endpoints
\end{itemize}

\subsection{State Management}

\begin{itemize}[noitemsep]
  \item \texttt{useQuery('member', getMember)} --- Caches profile; refetch on window focus
  \item \texttt{useQuery('events', listEvents)} --- Paginated events list
