\section{System Overview}
% ══════════════════════════════════════════════════════════════════════════════

\subsection{Problem Summary}

The CSEDU Students' Club requires a centralized digital platform to manage membership,
governance, meetings, elections, events, certificates, and finance with transparent,
role-controlled workflows. Previously fragmented and manual processes increased
administrative overhead and made constitutional compliance difficult to enforce.

\subsection{Target Users}

\begin{itemize}[noitemsep]
  \item General Members (current CSEDU students)
  \item Executive Committee (EC) members (posts and executive members)
  \item Moderator(s) (department student advisor role)
  \item Chief Patron (department chairman)
  \item Election Commissioners
  \item Alumni (limited dashboard access)
  \item System Admin (technical/role administration)
\end{itemize}

\subsection{Project Goals}

\begin{itemize}[noitemsep]
  \item Provide role-based secure access to all club operations.
  \item Digitize member lifecycle management, including cancellations and approvals.
  \item Implement governance and constitution workflows with approval tracking.
  \item Support election lifecycle: creation, candidacy, validation, voting, and results.
  \item Manage events and volunteer workflows with review and status updates.
  \item Enable meetings with attendance, absence alerts, and online/offline mode support.
  \item Implement certificate request, moderator/chairman review, and controlled download.
  \item Maintain financial transactions and ledger visibility for authorized roles.
\end{itemize}

\subsection{Out of Scope (Current Version)}

\begin{itemize}[noitemsep]
  \item Native mobile applications (Android/iOS) in this release.
  \item Direct university ERP/academic system integration.
  \item Full payment gateway integration for transactions/events.
  \item Automatic production-grade video token backend for all meeting providers.
\end{itemize}

\begin{tcolorbox}[significancestyle]
This SDD version reflects the implemented web-based architecture (React + Express + MongoDB)
and should be used as the baseline for detailed component, data, and flow design in later sections.
\end{tcolorbox}

\section{Architecture Design}
% ══════════════════════════════════════════════════════════════════════════════

\subsection{High-Level Architecture}

\subsubsection{Main Components / Services}

\begin{itemize}[noitemsep]
  \item \textbf{Presentation Layer (Frontend - React + Vite)}
  \begin{itemize}[noitemsep]
    \item Public shell: home, constitution, notices, events, about, contact.
    \item Dashboard shell: protected role-based pages for membership, governance, meetings, elections, events, finance, certificates, admin.
    \item API client with token refresh and centralized error normalization.
  \end{itemize}

  \item \textbf{Application Layer (Backend - Express)}
  \begin{itemize}[noitemsep]
    \item Route modules grouped by domain: auth, governance, membership, meetings, elections, events, finance, moderator, admin, certificates.
    \item Controller layer for HTTP request/response orchestration.
    \item Service layer for business rules and workflow transitions.
  \end{itemize}

  \item \textbf{Cross-Cutting Middleware}
  \begin{itemize}[noitemsep]
    \item Authentication middleware (JWT access token verification).
    \item Authorization middleware (permission-key based guard).
    \item Request validation middleware (Zod schemas).
    \item Request audit metadata middleware.
    \item Centralized error handling and not-found handling.
  \end{itemize}

  \item \textbf{Persistence Layer (MongoDB + Mongoose)}
  \begin{itemize}[noitemsep]
    \item Domain collections: User, Member, Role, Permission, UserRole, RolePermission.
    \item Governance/election collections: EcTerm, EcPost, EcAppointment, Election, ElectionCandidate, Vote, ConstitutionDocument, GovernanceProposal.
    \item Operations collections: Event, EventPost, EventComment, Volunteer, Meeting, MeetingAttendance, Transaction, MembershipCancellation, CertificateRequest, AuditLog.
  \end{itemize}
\end{itemize}

\subsubsection{Data Flow Summary}

\begin{enumerate}[noitemsep]
  \item Client requests protected data or action from dashboard pages.
  \item Frontend API client adds bearer token and calls backend endpoint under \texttt{/api/v1/*}.
  \item Backend applies middleware chain: authenticate \rightarrow authorize \rightarrow validate.
  \item Controller delegates business rules to service class.
  \item Service performs Mongoose operations, state transitions, and audit logging.
  \item Controller returns standardized JSON payload (success/data/message).
  \item Frontend updates query cache and re-renders page state.
\end{enumerate}

\subsubsection{External Integrations (If Any)}

\begin{itemize}[noitemsep]
  \item \textbf{MongoDB:} Primary persistent datastore for all domain entities.
  \item \textbf{ZegoCloud UI Kit (Web):} Integrated in meeting live page for online rooms.
  \item \textbf{Current Status:} Zego integration is client-side for room rendering; production-grade backend token service is a pending hardening item.
\end{itemize}

\subsubsection{Uniqueness Constraints}
\begin{itemize}[noitemsep]
  \item \texttt{User.email} unique.
  \item \texttt{Member.userId} unique; \texttt{Member.studentId} unique.
  \item \texttt{Role.name} unique; \texttt{Permission.key} unique.
  \item \texttt{UserRole(userId, roleId, startsAt)} composite unique.
  \item \texttt{RolePermission(roleId, permissionId)} composite unique.
  \item \texttt{ElectionCandidate(electionId, memberId, postId)} composite unique.
  \item \texttt{Vote(electionId, voterMemberId, candidateId)} composite unique.
  \item \texttt{Volunteer(eventId, memberId)} composite unique.
  \item \texttt{MeetingAttendance(meetingId, memberId)} composite unique.
  \item \texttt{Meeting.roomId} unique with sparse index (only for online meetings).
  \item \texttt{CertificateRequest.certificateNo} unique sparse.
\end{itemize}

\subsubsection{Nullability and Required Fields}
\begin{itemize}[noitemsep]
  \item Required identity fields: email, passwordHash, firstName, lastName.
  \item Required membership fields: userId, studentId, batch, currentYear.
  \item Optional workflow actor fields (e.g., review actor IDs) remain null until action completion.
  \item \texttt{Meeting.roomId} is nullable for offline meetings and required in practice for online flows.
  \item \texttt{Transaction.chequeSignedBy} and \texttt{chequeSignedAt} are nullable until cheque signing.
\end{itemize}

\subsubsection{Validation Rules}
\begin{itemize}[noitemsep]
  \item Enum-based state control is used extensively (meetingMode, election status, candidate status, certificate status, cancellation status, etc.).
  \item API-level request validation is enforced via Zod schemas in route middleware.
  \item Date fields are validated and normalized before persistence in service/controller flow.
  \item Business validations (eligibility, approval sequencing, role capability checks) are centralized in service classes.
\end{itemize}

\section{Security and Access Design}
% ══════════════════════════════════════════════════════════════════════════════

\subsection{Authentication Approach}

\begin{itemize}[noitemsep]
  \item Authentication is based on JWT access tokens issued after successful login.
  \item Refresh endpoint support is used to renew session state without repeated credential prompts.
  \item Protected API calls pass bearer tokens and are rejected when token verification fails.
  \item Passwords are stored as secure one-way hashes, never in plaintext.
\end{itemize}

\subsection{Authorization Model (Roles/Permissions)}

\begin{itemize}[noitemsep]
  \item Authorization uses a role-to-permission mapping model instead of static role checks only.
  \item \texttt{UserRole} and \texttt{RolePermission} collections resolve effective access for each request.
  \item Endpoint guards enforce permission keys at route level via authorize middleware.
  \item Domain workflows (e.g., moderator review, chairman approval, admin-only actions) are additionally enforced in services.
\end{itemize}

\subsection{Sensitive Data Handling}

\begin{itemize}[noitemsep]
  \item User credentials: password hashes only; no raw password persistence.
  \item Personally identifiable data (student ID, contact/profile attributes) is exposed based on least-privilege route design.
  \item Security-critical fields (role assignments, approval states, financial records) are changed only through authenticated and authorized endpoints.
  \item Validation and normalization are enforced at API boundaries to reduce malformed or unsafe payload persistence.
\end{itemize}

\subsection{Audit/Logging Plan}

\begin{itemize}[noitemsep]
  \item Request-level metadata is collected by audit middleware for traceability.
  \item Domain services emit audit events for critical actions: approval/rejection, role updates, financial writes, vote-sensitive operations, and certificate issuance/download.
  \item \texttt{AuditLog} stores actor, action, resource, resource ID, request correlation ID, and metadata snapshot.
  \item Error handling returns sanitized client responses while preserving actionable server logs for diagnostics.
\end{itemize}

\begin{tcolorbox}[significancestyle]
The security model follows a defense-in-depth path: token verification, permission gates, schema validation, service-level rule enforcement, and audit persistence.
\end{tcolorbox}

\section{Implementation Plan}

\subsection{Sprint 1 Completed Features}

\begin{itemize}[noitemsep]
  \item Core platform foundation: frontend routing shell, backend API bootstrap, standardized response/error handling.
  \item Authentication and access-control baseline with role/permission guard chain.
  \item Membership and governance modules including cancellation workflow and constitution/proposal handling.
  \item Election module: term/post/candidate management, validation states, voting and result publication path.
  \item Events and volunteering workflow with review/approval lifecycle.
  \item Meeting workflow with online/offline mode support and live room integration path.
  \item Certificate request workflow with moderator/chairman approval chain and controlled issuance.
  \item Finance and audit foundations with transaction records and action trace logging.
\end{itemize}

\subsection{Pending Features for Sprint 2}

\begin{itemize}[noitemsep]
  \item Production-hardened meeting token generation service (server-side provider token strategy).
  \item Full notification channel improvements (meeting reminders, approval transitions, absence alerts).
  \item Enhanced reporting dashboards for elections, participation, and finance analytics.
  \item UX and accessibility hardening across long workflows (mobile responsiveness and edge-state handling).
  \item Optional integration work: payment gateway pilot and external institutional system hooks.
\end{itemize}

\subsection{Technical Risks}

\begin{itemize}[noitemsep]
  \item Permission drift risk as roles and workflow states evolve quickly.
  \item Third-party real-time meeting dependency risk (token/session reliability).
  \item Data consistency risk in multi-step approvals if partial failures occur.
  \item Performance risk for large audit/event datasets without index tuning and query shaping.
\end{itemize}

\subsection{Mitigation Plan}

\begin{itemize}[noitemsep]
  \item Maintain permission matrix review at each sprint boundary and add regression checks for guarded routes.
  \item Move live meeting credentials/tokens to backend-managed secure issuance with expiration controls.
  \item Introduce stricter transaction boundaries and idempotency checks for approval transitions.
  \item Monitor slow queries, add targeted MongoDB indexes, and paginate high-volume feeds/log views.
\end{itemize}

\begin{itemize}[noitemsep]
  \item Service-layer business rules: eligibility checks, status transitions, approval sequencing.
  \item Permission utility and middleware logic for allow/deny outcomes.
  \item Validation schemas and DTO normalization rules.

\subsection{Integration Testing Targets}

\begin{itemize}[noitemsep]
  \item Auth flow: login, token-protected API access, refresh path, unauthorized edge cases.
  \item Meeting flow: create online/offline, room access constraints, attendance recording.
  \item Certificate flow: submit request, moderator review, chairman review, issuance state change.
  \item Election flow: candidate registration, validation, vote casting, result publication.
  \item Membership cancellation flow: request-to-final-execution transitions.
\end{itemize}

\subsection{E2E Testing Targets}

\begin{itemize}[noitemsep]
  \item Member journey from authentication to dashboard actions with role-appropriate visibility.
  \item EC/Moderator governance journey for approvals and constitution-related actions.
  \item Event + volunteer journey from publish to application review outcome.
  \item Certificate lifecycle from request submission to final user download.
\end{itemize}

\subsection{Known Hard-to-Test Areas}

\begin{itemize}[noitemsep]
  \item Real-time meeting provider behavior under unstable network conditions.
  \item Time-dependent and concurrency-sensitive transitions in elections and approvals.
  \item Cross-role race conditions when multiple reviewers act on the same record.
  \item Long-lived session behavior across refresh/re-login boundary scenarios.
\end{itemize}

\begin{tcolorbox}[summarybox]
Testing depth will prioritize service and integration levels first, then stabilize E2E suites for critical business journeys.
\end{tcolorbox}
